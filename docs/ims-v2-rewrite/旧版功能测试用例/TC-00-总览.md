## 1. 编写原则（铁律）

1. **依据优先级（v0.3）**：功能、字段、流程、业务规则、错误码、权限与菜单可见性以 **PRD（含 doc/产品规格 V1～V3，v0.3.1 确认产品规格视同 PRD）** 为准；PRD 已定义而实现缺失或不一致 → **不通过**（不是阻塞）。原型（`doc/UI原型`）只约束 PRD 未规定的纯布局/视觉细节，以及 PRD 未定义的附加功能（这类用例在依据列注明「PRD 未规定，保留原型」）。
2. **像人一样操作**：每条用例都从侧栏菜单进入，通过点击按钮、Tab、下拉，在输入框里打字完成；**禁止**直接输入 URL 跳转、禁止用接口/SQL 代替任何操作步骤。接口、数据库只允许在操作完成后用来**辅助核对**结果。
3. **数据靠功能用例产生**：不预置种子数据。缺数据时先执行产生该数据的用例，「前置」列写明来源用例编号。开发环境数据可随意新增删除。
4. **账号**：admin / Admin@123（R1 系统管理员）。其他角色用户（U-R2～U-R11 等）由 TC-01 系统管理页面创建。
5. **第三方依赖**（钉钉、Football WebAPI / live_room、平台 Cookie 采集、AI 模型）按测试桩/测试企业执行，相关用例标「可能阻塞」。
6. **预期值**：只写文档里能找到的具体值；文档没细化的写「定性判定」。

## 7. 执行约定

- **截图**：每条用例至少 3 张——进入页面（含侧栏与面包屑）、关键操作（如填写完的表单/确认弹窗）、结果（列表/提示/状态变化）。文件名：`用例编号-序号.png`。
- **结果判定**：
  - **通过**：实际与预期一致。
  - **不通过**：与 PRD 口径不一致，**包括 PRD 已定义的功能/字段/入口在系统里找不到**；写「实际结果」并附截图。
  - **阻塞**：仅限 外部依赖不可用（钉钉/Football/采集器/AI 模型）、或前置数据因上游用例不通过而无法产生；须写卡点和受影响的后续用例。
- **与原型比对**：只在 PRD 未规定的布局/视觉细节上与原型比对；与原型不同但符合 PRD 的，判通过。
- 执行时禁止为了「绕过」问题而改用 URL 或接口；需要用接口/数据库核对时，在备注里写明核对语句与结果。
