## 3. 主键是否超过 2^53（9007199254740992）

### 3.1 证据
- 方法：① 读所有表的 `information_schema.tables.AUTO_INCREMENT`；② 对 4 个库里所有 bigint / decimal 列做 `MAX(col)` 和 `SUM(col > 2^53)`（1,717 列；`shenyuDB` 行数超过 20 万的 4 张大表只看了 AUTO_INCREMENT）；③ 对 `shenyuDB` 里 varchar 类型的 `creator` 列抽查。

| 库 | 最大 AUTO_INCREMENT | 所有 bigint 列的最大值 | 有没有超过 2^53 |
|---|---|---|---|
| `ims` | 4,153（`ims_role_perm_detail`） | 70,070（`ims_auth_user_dept.dept_id`） | 没有 |
| `opsbiz`（含 `live_room` 桩表：0 行，AUTO_INCREMENT=1） | 900,002（`oa_author`，桩数据号段） | 2,400,000（播放数，不是 id） | 没有 |
| `ai_platform` | 63 | 50,000（金额） | 没有 |
| `shenyuDB` | **2,059,567,794,397,171,713（`system_users`）**；其余表最大约 4,590,271 | 见下 | **有** |

- `shenyuDB` 里超过 2^53 的值：
  - **`system_users.id`**：69 个用户里有 **8 个**超过 2^53（雪花 id，`1749825673829120001`～`2059567794397171712`；tenant 1 有 5 个，其中包括最早的管理员；tenant 2、3、4 各 1 个）。其余 61 个 id 在 100～200 之间。
  - 引用这些用户 id 的列也有大值：`system_user_role.user_id`（4 行）、`system_user_author.user_id`（13）、`identity_apply.approver_id`（6）、`author_pv_log.user_id`（138），以及登录、操作、令牌、错误日志里的 `user_id`；`system_operate_log.biz_id`（2）；varchar 类型的 `creator` 里也存着雪花 id 字符串（`system_users` 2 行、`author_user` 1 行）。
  - 与 IMS 无关：`mp_message.msg_id`（17,832 行，微信消息 id）、Flowable `ACT_HI_VARINST.LONG_`（3 行）。这些不迁移。
- `live_room.author_id` 对应 `author_user.id`：最大值 1,000,008，没有超过 2^53。
- 真实 `live_room.id`：类型 bigint(20) AUTO_INCREMENT 已确认（见 §1）；最大值与当前 AUTO_INCREMENT 上线前联调时在 `shenyu-live` 上查询即可，**不阻塞 B0a**（附件 DDL 导出时 `AUTO_INCREMENT` 约 203 量级，远低于 2^53）。

### 3.2 结论
1. 旧 IMS、opsbiz、ai_platform 的主键都远低于 2^53。
2. **Football 用户表有 8 个雪花 id 超过 2^53。** 按 01 清单和 ADR-009 的“导入用户保留原主键，序列起点 = 最大值 + 1”：
   - 这 8 个用户的 id 在 JSON 数字里会丢精度（前端拿到的值和库里不一样）；
   - 同时，`ims_sys_user` 的自增起点会变成 2,059,567,794,397,171,713。**之后新建的每个用户 id 也都超过 2^53。**
3. 因此 04-B-05 预设的条件已经成立：**需要打开 id 字符串输出**，或者改变用户导入的主键策略。两种做法：
   - **方案 A（推荐，符合 ADR-009）**：保留原主键，B0a 起默认 `api.id_as_string=true`，前端和组件一律把 id 当字符串处理。
   - **方案 B**：这 8 个雪花 id 迁移时重新分配小 id，另建旧 id → 新 id 映射表，接口继续输出数字。这样违背“保留原主键”，要改 ADR-009。
   - 选哪个方案由产品裁定，必要时请 zhang wu 决策。
