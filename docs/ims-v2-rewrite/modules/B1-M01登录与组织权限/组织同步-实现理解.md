## 2. API 契约

### 2.1 新增接口（14 个，含回调）

#### 2.1.1 组织同步概览

```
GET /admin-api/ims/auth/org/sync-metrics
```

**权限**：`ims:system:org-sync:query`

**响应**：
```json
{
  "code": 0,
  "data": {
    "userTotal": 1234,
    "yesterdayEventCount": 56,
    "pendingEventCount": 3,
    "deadEventCount": 1,
    "avgDelayMinutes": 2.5,
    "p95DelayMinutes": 4.8,
    "successRate24h": 0.98,
    "dingtalkUnavailable": false,
    "reconcileFailedTwice": false
  }
}
```

**规则**：
- `userTotal`：状态为在职（ACTIVE）或冻结（FROZEN）的用户数，不含离职
- `avgDelayMinutes`：最近 24 小时成功事件的 `(processed_time - event_time)` 平均值，保留 1 位小数
- `dingtalkUnavailable`：最近 10 分钟内有钉钉调用超时（5003）记录
- `reconcileFailedTwice`：最近两个对账批次均失败

#### 2.2.2 钉钉回调扩展（依赖 PR #20 合入后）

扩展 `GET /admin-api/ims/auth/sso/dingtalk/callback` 与 `POST /admin-api/ims/auth/sso/dingtalk/h5-login`：

- 映射与手机号都未命中时，调用 FP-B1-LG-07 即时同步
- 即时同步成功后正常签发
- 钉钉中**不在本企业**或钉钉侧**已离职**且 IMS 无对应用户 → `1217`
- **本企业在职的**，即时建人并登录（即使原先无映射）

**1216 与 1217 的边界**：
- `1216`：IMS 里**已有对应用户**且状态为**冻结（`FROZEN`）或离职（`RESIGNED`）**→ 返回 1216「账号已冻结或已离职，无法登录」
- `1217`：钉钉侧不在本企业，或钉钉侧已离职且 IMS 里**没有映射**→ 返回 1217「未找到与钉钉账号对应的用户，请联系管理员」

**处理流程**（先完整拉取校验、在内存比对、再分段写入）：

1. 检查是否有正在进行的对账 → 有则 `1001`
2. 创建 `OrgSyncBatch`，状态 `RUNNING`

**本期钉钉对接模型**【已定】：
- 本期只对接**一个钉钉企业内部应用**
- `callback_token`、`callback_aes_key`、`app_key`、`corp_id` 全局配置一份，从环境变量读取

  - **评审决定**：receiveid 使用 AppKey
- 若 `receiveid` 不匹配 → 返回 1008（不是本应用的回调）

**验签算法**（钉钉官方规范，本 PR 新建实现）：

1. 从 query 取 `msg_signature`、`timestamp`、`nonce`（注：钉钉 query 参数名是 `msg_signature`）
2. 从 body 取 `encrypt`
3. 将 `callback_token`、`timestamp`、`nonce`、`encrypt` **排序后拼接**
4. 对拼接结果做 **SHA1** 哈希
5. 与 `msg_signature` 比对

```python
import hashlib
import hmac

def verify_callback_signature(
    token: str,           # 服务端配置的 callback_token
    timestamp: str,       # query 参数
    nonce: str,           # query 参数
    encrypt: str,         # body 中的 encrypt 字段
    msg_signature: str,   # query 参数（注：钉钉用 msg_signature）
) -> bool:
    to_sign = "".join(sorted([token, timestamp, nonce, encrypt]))
    expected = hashlib.sha1(to_sign.encode()).hexdigest()
    return hmac.compare_digest(expected, msg_signature)
```

**处理流程**【已定】（验签 → 防重放 → 解密 → receiveid 校验 → 租户匹配）：

> 注：CorpId 在密文里，必须先解密才能匹配租户。

1. **验签**：校验 msg_signature，失败 → HTTP 200 + 1008，不写事件，记日志
2. **防重放**：
   - `timestamp` 超过 5 分钟 → HTTP 200 + 1008
   - `nonce` 在 Redis 已存在（TTL 10 分钟） → HTTP 200 + 1008
3. **AES 解密**：解密 `encrypt` 字段，失败 → HTTP 200 + 1008
4. **receiveid 校验**：校验明文尾部 `receiveid == settings.dingtalk.app_key`，不匹配 → HTTP 200 + 1008
5. **租户匹配**：解析解密后事件体中的 `CorpId`，与配置的 `settings.dingtalk.corp_id` 比对
   - 不匹配 → HTTP 200 + `{"code": 0}`，不写事件，记日志
6. **幂等**：按 `event_id` 去重，已存在则返回成功
7. **写事件**：写 `OrgSyncEvent`（`status=PENDING`）
8. **返回加密 success**

**AES 加解密**（使用 `cryptography` 库，不引入 `pycryptodome`）：

**明文结构**：`random(16) + msg_len(4, 大端) + msg + receiveid`
- 16 字节随机前缀
- 4 字节大端消息长度
- 消息体
- receiveid（企业内部应用填 AppKey）

**PKCS#7 填充**：块大小按钉钉官方 SDK 使用 **32 字节**

```python
import base64
import hashlib
import secrets
import struct

from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.backends import default_backend
from app.core.clock import get_now

BLOCK_SIZE = 32  # 钉钉官方 SDK 使用 32 字节块大小


def _pkcs7_pad(data: bytes, block_size: int = BLOCK_SIZE) -> bytes:
    """PKCS#7 填充。"""
    pad_len = block_size - (len(data) % block_size)
    return data + bytes([pad_len] * pad_len)


def _pkcs7_unpad(data: bytes) -> bytes:
    """去除 PKCS#7 填充。"""
    pad_len = data[-1]
    return data[:-pad_len]


def decrypt_callback(aes_key: str, encrypt: str, expected_receiveid: str) -> str:
    """
    AES-256-CBC 解密（使用 cryptography 库）。
    
    明文结构：random(16) + msg_len(4, 大端) + msg + receiveid
    - key = Base64Decode(aes_key + '=')（补等号后解码，得 32 字节）
    - IV = key 前 16 字节
    - 解密后去 PKCS#7 填充（块大小 32）
    - 从 [16:20] 取 4 字节大端长度
    - 校验尾部 receiveid == expected_receiveid
    
    Args:
        aes_key: 43 字符 Base64 编码的 AES key
        encrypt: Base64 编码的密文
        expected_receiveid: 企业内部应用填 AppKey
    """
    key = base64.b64decode(aes_key + "=")
    iv = key[:16]
    cipher = Cipher(algorithms.AES(key), modes.CBC(iv), backend=default_backend())
    decryptor = cipher.decryptor()
    decrypted = decryptor.update(base64.b64decode(encrypt)) + decryptor.finalize()
    decrypted = _pkcs7_unpad(decrypted)
    # 解析：random(16) + msg_len(4) + msg + receiveid
    msg_len = struct.unpack(">I", decrypted[16:20])[0]
    msg = decrypted[20:20 + msg_len].decode()
    receiveid = decrypted[20 + msg_len:].decode()
    if receiveid != expected_receiveid:
        raise ValueError("receiveid mismatch")
    return msg


def encrypt_callback(aes_key: str, msg: str, receiveid: str) -> str:
    """
    AES-256-CBC 加密（使用 cryptography 库）。
    
    明文结构：random(16) + msg_len(4, 大端) + msg + receiveid
    - 企业内部应用 receiveid 填 AppKey
    """
    key = base64.b64decode(aes_key + "=")
    iv = key[:16]
    # 构造明文：random(16) + msg_len(4) + msg + receiveid
    random_bytes = secrets.token_bytes(16)
    msg_bytes = msg.encode()
    receiveid_bytes = receiveid.encode()
    plaintext = random_bytes + struct.pack(">I", len(msg_bytes)) + msg_bytes + receiveid_bytes
    plaintext = _pkcs7_pad(plaintext, BLOCK_SIZE)
    # 加密
    cipher = Cipher(algorithms.AES(key), modes.CBC(iv), backend=default_backend())
    encryptor = cipher.encryptor()
    encrypted = encryptor.update(plaintext) + encryptor.finalize()
    return base64.b64encode(encrypted).decode()


def sign_callback(token: str, timestamp: str, nonce: str, encrypt: str) -> str:
    """生成回调签名（SHA1）。"""
    to_sign = "".join(sorted([token, timestamp, nonce, encrypt]))
    return hashlib.sha1(to_sign.encode()).hexdigest()
```

**成功应答**（必须返回加密的 success）：

```python
def encrypt_response(token: str, aes_key: str, app_key: str) -> dict:
    """返回加密的 success 响应。
    
    Args:
        token: 服务端配置的 callback_token，用于签名
        aes_key: 服务端配置的 callback_aes_key，用于加密
        app_key: 企业内部应用的 AppKey，作为 receiveid
    """
    nonce = secrets.token_hex(8)
    timestamp = str(int(get_now().timestamp()))  # 使用可注入时钟
    msg = "success"
    encrypt = encrypt_callback(aes_key, msg, app_key)
    signature = sign_callback(token, timestamp, nonce, encrypt)
    return {
        "msg_signature": signature,
        "timeStamp": timestamp,
        "nonce": nonce,
        "encrypt": encrypt,
    }
```

2. **H5 免登**：`POST /admin-api/ims/auth/sso/dingtalk/h5-login`

**处理流程**：
1. 用钉钉 userid 调钉钉接口获取人员详情（由 `HttpxDingTalkLoginClient.get_user_detail` 实现，见 §11.1）
2. 在职且属于本企业 → 按 FP-D07-03 建本地用户和映射
3. 写 `OrgSyncEvent`（`biz_type=HIRE`，`event_id=login-sync:<钉钉userid>:<日期>`）
4. 触发岗位供给（调用 `PositionSupplyService.deliver`，不修改该服务）
5. 签发令牌
6. 钉钉接口报错 → `1006`（记登录日志）
7. 确认不在本企业或钉钉侧已离职 → `1217`（见 §2.2.2 边界说明）
8. 钉钉超时 → `5003`

**错误码统一**（扫码回调和 H5 免登两条路径各有测试覆盖）：

| 场景 | 错误码 | 说明 |
|-----|-------|------|
| 钉钉接口报错 | 1006 | 记登录日志，提示"钉钉登录失败，请重新扫码" |
| 钉钉侧不在本企业或已离职且 IMS 无映射 | 1217 | 提示"未找到与钉钉账号对应的用户，请联系管理员" |
| IMS 已有用户且状态为**冻结或离职** | 1216 | 提示"账号已冻结或已离职，无法登录" |
| 钉钉超时 | 5003 | 提示"钉钉服务异常，请稍后再试" |

**并发首登处理**【已定】（UT-B1-LG-07-CONCURRENT）：

**唯一约束与事务规则**：
- **任何 `IntegrityError`（无论是建用户还是写映射时触发）都必须整体回滚**
- 回滚后**先按 dingtalk userid 重查映射**，查到就直接签发令牌
- 查不到，才说明是真正的非并发撞名，这时再走加后缀的逻辑

**映射唯一索引**：`uk_mapping_dingtalk(tenant_id, dingtalk_user_id, deleted)`
- 使用 main 的 soft delete 机制（`app/db/base.py`）：活跃记录 `deleted=0`，删除时 `deleted=<row id>`
- 因此**活跃记录在 (tenant_id, dingtalk_user_id) 上是唯一的**，删后重建不会撞唯一键
- 不需要再新增两列的索引

**事务处理流程**：
- **建用户和写映射放在同一个事务里**
- 用户名或映射写入时如果违反唯一约束 → **回滚整个事务**（包括刚建的用户）
- 回滚后**先按 dingtalk userid 重查映射**：
  - 查到映射 → 用对应的用户签发令牌（并发场景，另一个请求已成功）
  - 查不到映射 → 说明是非并发撞名（如 `manager123` 已被其他钉钉用户占用），走加 `_2` 逻辑重试

**UT-B1-LG-07-CONCURRENT 测试口径**：
- **必须在真实 MySQL 上跑**，不能用 SQLite
- 用**两个独立的数据库连接**（两个会话）同时发起首次登录
- 用 **barrier**（如 `threading.Barrier`）：两边都已查过「映射不存在」、**即将插入时**用 barrier 同时开始插入，让其中一边真的等锁，然后报 duplicate key
  - InnoDB 里第二个事务会阻塞在行锁上，两边「同时提交」做不到
  - barrier 位置在插入前，不是提交前
- **不能**顺序调用两次，**不能** mock 掉唯一约束
- 断言：
  - `ims_sys_user` 只有 **1 条**记录
  - `ims_auth_user_mapping` 只有 **1 条**记录
  - **没有带序号的多余用户**（如 `manager123_2`）
  - **事务回滚路径确实走到了**：
    - 方式一：对回滚分支的**计数器断言恰好等于 1**
    - 方式二：用 **caplog 断言出现一条指定的日志事件**
    - 二选一，必须写明

**username 生成规则**【已定】：
- 格式：`user_id[:50]`，即钉钉 userid 截取前 50 字符（如 `manager123`）
- **不加 `dt_` 前缀**（维持 main 现状）
- 数据库 `username` 列长度上限：50 字符（见 `migrations/versions/001_initial.py`）
- 与 main 现有逻辑一致（`dingtalk_login.py` 中 `username=(identity.user_id or "")[:50]`）

**username 撞名处理**（通用规则）：
- 公式：`username = user_id[:50-len(suffix)] + suffix`
- 首次尝试：`user_id[:50]`（无后缀）
- 撞名后重试：依次尝试 `_2`、`_3`……直到成功
- 示例：`user_id` 本身 49 字符，撞名后变成 `user_id[:47]_2`（保证总长度 ≤50）
- **UT-B1-LG-07-USERNAME-COLLISION 测试口径**：
  - 两个**不同的钉钉 userid**，但它们的**前 50 字符相同**
  - 两者**并发登录**
  - 断言：一个用户 username 无后缀，另一个用户 username 带 `_2` 后缀

**即时同步 event_id 规则**：
- 格式：`login-sync:<钉钉userid>:<日期>`（如 `login-sync:manager123:2026-10-13`）
- **日期使用北京时间当天**
- 需补一条**跨零点重复登录**的测试（23:59 和 00:01 各登录一次，应产生两条事件）

**幂等规则**：同一钉钉 userid 当天已有成功的即时同步事件则不重复处理

### 4.5 用户删除与会话失效

**删除限制**：
- **只有从未登录过的用户才能删除**（`last_login_time IS NULL`）
- 已登录过的用户只能冻结或离职，不能删除
- 试图删除已登录过的用户 → 返回 `1001`「参数校验失败」

**删除行为**：
- 用户被删除时（使用 main 的 soft delete：`deleted=<row id>`），调用 `UserService._drop_sessions` 踢人
- **踢人机制**：会话 key + Redis 黑名单（TTL ≥ access-token TTL），**不用 token_version+1**
- 之后该用户的所有请求（包括刷新令牌）返回 `1002`「登录已失效，请重新登录」

**perm_version 存放位置**：
- Redis key：`ims:perm_ver:u/{user_id}`（用户级）和 `ims:perm_ver:t/{tenant_id}`（租户级）

**最后一个 R1 保护**：
- **最后一个在职 R1 不能移除**（不能冻结、离职或删除）
- 试图移除 → 返回 `1001`「参数校验失败」

**测试用例**：见 §7 E2E 用例。

### 4.6 租户停用与过期

**裁决**：租户停用或过期时，登录、刷新和在线请求都返回 1008。

**行为**：
- 租户 `status=DISABLED` 或已过期时
- 登录接口、刷新令牌接口、所有在线请求均返回 `1008`
- **msg 固定为「所属组织已停用，请联系管理员」**（此场景是唯一自定义 1008 msg 的地方，区别于普通权限不足）

**平台租户**：
- 平台租户（`is_platform=True`）不可停用
- 试图停用平台租户 → 返回 `1001`「参数校验失败」

### 4.7 数据范围过滤

- 事件：按 `dept_id` 过滤
- 人员：按主部门和所属部门过滤
- 对账明细：按 `dept_id` 过滤
- **统计卡和对账汇总数字为全公司口径**
- **本地部门同等参与数据范围**

数据范围规则（Q10 已核实）：
- R2 `data_scope=DEPT`：本部门，不含下级
- R4 `data_scope=IP_GROUP`：按 IP 组

### 11.3 事件回调安全

**回调接口**：`POST /admin-api/ims/callback/dingtalk/event`（本 PR 新建，含 SHA1 验签逻辑）

**服务端配置**（`DingTalkSettings`）：
- `callback_token`：验签用的 token
- `callback_aes_key`：加解密用的 AES key（43 字符 Base64）

**验签算法**（本 PR 新建实现）：
```python
import hashlib
import hmac

def verify_callback_signature(
    token: str,           # 服务端配置的 callback_token
    timestamp: str,       # query 参数
    nonce: str,           # query 参数
    encrypt: str,         # body 中的 encrypt 字段
    msg_signature: str,   # query 参数（钉钉用 msg_signature）
) -> bool:
    to_sign = "".join(sorted([token, timestamp, nonce, encrypt]))
    expected = hashlib.sha1(to_sign.encode()).hexdigest()
    return hmac.compare_digest(expected, msg_signature)
```

**处理流程顺序**【已定】（与 §4.2、§2.1.14、§8.5 保持一致）：

> 注：CorpId 在密文里，必须先解密才能匹配。

1. 验签（失败 → 1008）
2. 防重放（失败 → 1008）
3. AES 解密（失败 → 1008）
4. receiveid 校验（不匹配 → 1008）
5. CorpId 匹配：与配置的 `settings.dingtalk.corp_id` 比对（不匹配 → code 0，不写事件，记日志）
6. 写事件

**AES 加解密**：
- 使用 `cryptography` 库，**不引入 `pycryptodome`**
- 明文结构：`random(16) + msg_len(4, 大端) + msg + receiveid`
- PKCS#7 块大小：**32 字节**（按钉钉官方 SDK）
- key = Base64Decode(aes_key + '=')
- IV = key 前 16 字节
- receiveid 填 `app_key`（企业内部应用走事件订阅）

**成功应答**：必须返回加密的 success（msg_signature/timeStamp/nonce/encrypt）

**单测**：
- 使用**官方 SDK 生成的往返向量**做验签和加解密测试
- 向量生成方式：调用钉钉官方 Java/Python SDK 的加解密方法，记录输入输出

**防重放**：
- `timestamp` 超过 5 分钟 → 拒绝
- `nonce` 在 Redis 去重（key: `dingtalk:nonce:{nonce}`，TTL 10 分钟）

**验签失败或重放响应**：
- HTTP 200 + `{"code": 1008, "msg": "暂无权限"}`（使用 main 已有的 1008 文案，**不自定义 msg**）
- **不写事件**
- **记日志**

### 11.5 LG-07 首登即时同步

**本 PR 必须真跑通**，两条路径都需要：

1. **扫码回调路径**：`GET /admin-api/ims/auth/sso/dingtalk/callback`
2. **H5 免登路径**：`POST /admin-api/ims/auth/sso/dingtalk/h5-login`

**处理流程**：
1. 钉钉扫码/免登回调时，映射和手机号都未命中
2. 调用钉钉接口获取人员详情（`HttpxDingTalkLoginClient.get_user_detail`）

5. 触发岗位供给 `PositionSupplyService.deliver()`
6. 签发令牌
7. 钉钉接口报错 → `1006`
8. 钉钉侧不在本企业/已离职且 IMS 无映射 → `1217`
9. IMS 已有用户且状态为**冻结或离职** → `1216`
10. 超时 → `5003`

**错误码覆盖**（扫码和 H5 各有测试）：

**并发首登**（UT-B1-LG-07-CONCURRENT）：

**唯一约束与事务规则**：
- **任何 `IntegrityError`（无论是建用户还是写映射时触发）都必须整体回滚**
- 回滚后**先按 dingtalk userid 重查映射**，查到就直接签发令牌
- 查不到，才说明是真正的非并发撞名，这时再走加后缀的逻辑

**映射唯一索引**：`uk_mapping_dingtalk(tenant_id, dingtalk_user_id, deleted)`
- 使用 main 的 soft delete 机制（`app/db/base.py`）：活跃记录 `deleted=0`，删除时 `deleted=<row id>`
- 因此**活跃记录在 (tenant_id, dingtalk_user_id) 上是唯一的**，删后重建不会撞唯一键
- 不需要再新增两列的索引

**事务处理流程**：
- 建用户和写映射放在**同一个事务**里
- 任何 `IntegrityError` → **回滚整个事务**
- 回滚后**先按 dingtalk userid 重查映射**：
  - 查到映射 → 用对应的用户签发令牌（并发场景）
  - 查不到映射 → 非并发撞名，走加后缀逻辑重试

**UT-B1-LG-07-CONCURRENT 测试口径**：
- 必须在**真实 MySQL** 上跑，不能用 SQLite
- 用**两个独立的数据库连接**同时发起首次登录
- barrier 位置：两边都已查过「映射不存在」、**即将插入时**用 barrier 同时开始插入
- 不能顺序调用两次，不能 mock 掉唯一约束
- 断言：
  - user 表 1 条、mapping 表 1 条
  - **没有带序号的多余用户**（如 `manager123_2`）
  - **回滚路径确实走到了**：计数器断言恰好等于 1，或 caplog 断言出现指定日志事件

**跨零点测试**：
