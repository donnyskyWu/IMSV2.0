> **评审对象**：公司管理层（老板/高管）、各业务部门负责人

## 一、规划总览

### 1.1 一句话定位

IMS 是一套「**以钉钉为组织底座、以虚拟资产为管理主线、以直播业务为价值核心**」的一体化管理平台：让**人、岗、权**实时对齐，让**资产、账号、直播、利润**全程可溯源，让**培训、会议、绩效、协作**从"靠人盯"变成"系统驱动"。

**它不是** 19 个独立功能的堆砌，而是**一条从"实名人"到"利润"的完整数据链**：人 → 岗位权限 → 领用的账号/资产 → 每场直播 → 成本与利润 → 绩效与分成。过去这条链断在 Excel、群聊和口头交接里；IMS 把它接起来。

### 1.2 分期全景表

| 期次 | 主题 | 需求范围 | 主要用户角色 | 核心业务价值 | 上线后一句话效果 |
|---|---|---|---|---|---|
| **第 0 阶段：准备期** | **打地基 —— 对接、清数据、定规则** | 钉钉对接、岗位模板梳理、历史 Excel 资产/账号清洗 | IT、人事、运营、产品 | 把"数据准、规则清"的前提准备好 | "系统还没上线，家底已经理顺了一半" |
| **第一期（V1）** | **系统基座 —— 把"人"和"资产"管起来** | 01 权限管理、07 资产管理、08 账号管理、10 直播管理（**P0**） | 全员、高管/老板、部门负责人、运营/主播、人事、IT | 权限零手工、资产可溯源、直播留痕 | "人员一入职权限就到位，每个账号都能查到是谁在用、哪场直播用了它" |

### 1.3 分期逻辑一览（为什么这么切）

| 逻辑 | 说明 |
|---|---|
| **先基座、后应用** | 01 权限管理是所有模块的通行证；07 资产管理 / 08 账号管理是所有业务数据的主键。没有它们，后面的直播、财务、绩效都是一盘散沙。 |
| **先"止血"、后"提效"** | 第一期（V1）解决的是**安全与失控**（权限滞后、账号丢失、封号无法溯源）；第二期（V2）/第三期（V3）解决的是**效率与决策**。先堵漏，再加速。 |
| **数据链路决定顺序** | 有资产台账（07）→ 才能有直播台账（10）→ 才能归集成本（11）→ 才能有利润看板与穿透（12）→ 才能算人效（19）。跨期是一条链，不能颠倒。 |
| **产生数据在前、消费数据在后** | 02/03/09/14 等"产生数据"的模块先上，05 绩效、13 预警吸收上游数据后再上；避免"系统上线了却没有数据可算"。 |
| **口径与模型必须前置** | 指标口径字典、IP 组组织模型、主数据关联模型若不前置，后期要么取不到数、要么需重算历史，返工代价极高（见附录 A 的 A1/A2/A3）。 |

### 2.3 节奏说明（为什么上调到约 40–52 周）

| # | 理由 | 说明 |
|---|---|---|
| 1 | **模块与需求基数大** | 19 个模块、80+ 用户故事、200+ 验收标准；第二期（V2）单期即含 10 个模块。 |

## 三、第一期（V1）详述：系统基座 —— 把"人"和"资产"管起来（P0）

### 3.1 期次定位与主题

**主题**：打通「人—岗—权」与「资产—账号—直播」两条主线，建立全系统的**主数据底座**，并**定版全链路数据模型**。
**一句话**：这一期不追求功能多，只追求**数据准、权限通、台账全、模型对**——它是后面所有模块的地基。

**覆盖需求与模块清单**

| 编号 | 模块 | 本期交付的二级功能 | 优先级 |
|---|---|---|---|
| 01 | 权限管理 | 单点登录（SSO）、组织架构同步、岗位模板管理、个人工作台 | P0 |
| 07 | 资产管理 | 资产档案录入、正向穿透查询、反向穿透查询 | P0 |
| 08 | 账号管理 | 账号领用、账号流转/收回、离职归还、领用记录时间线 | P0 |
| 10 | 直播管理 | 开播风控登记、下播数据录入、直播风险告警、历史台账查询 | P0 |
| — | **数据模型设计（独立交付项）** | 账号-资产-实名人-场次-成本-利润 的 ER 关系图、主键/外键字典、预留字段清单、场次 ID 编码规则 | P0 |

> **为什么数据模型要在第一期就做（业务语言）**：第三期（V3）要回答两个老板最关心的问题——"**这个实名人名下到底绑了多少资产？**"和"**这场直播的利润该找谁负责？**"。这两个问题要求"人—资产—场次—成本—利润"从一开始就被一条线串起来。如果第一期只把数据"存进去"、不预留它们之间的关联字段，到第三期再想串起来，就要把历史数据全部推倒重录，代价极高。**第一期多花几天定模型，第三期省下几周返工。**

### 3.2 面向不同角色的业务价值

| 角色 | 痛点（上线前） | 系统给的解法 | 业务价值 |
|---|---|---|---|
| **普通员工（剪辑/销售/主播/运营）** | 入职后要挨个找人开权限，等几天才能干活；不知道新账号该找谁领 | 钉钉登录即用（SSO）、岗位模板自动匹配权限；个人工作台一屏看到"我的账号、我的待办" | 入职当天即可开工，从"求人开权限"变成"登录即到位" |
| **部门负责人 / 直属上级** | 手下人能看什么、能操作什么全靠手工配，人员变动就漏配；账号发放靠口头 | 岗位模板统一授权、人员变动自动同步；账号领用/收回全部线上留痕、可随时查看团队资产分布 | 团队权限和账号"一屏尽览"，不再担心漏配和口头扯皮 |
| **人事管理员** | 入职/离职要手工整理权限清单和资产归还；离职人员账号常常收不回来 | 离职流程触发权限回收 + 账号归还提醒；证件与资产关联，交接有清单 | 离职交接从"追着要"变成"流程自动盯"，资产不流失 |
| **运营 / 主播** | 开播没登记，封号后不知道是哪台设备、哪个账号、谁在负责 | 开播前风控登记（账号/设备/人员），下播录入数据，直播历史台账可查 | 每场直播"有据可查"，封号时能分钟级定位到人和设备 |
| **财务负责人** | 账号、资产不清晰，后续成本归集不到场次 | 本期建立资产/账号台账与数据模型，为成本归集铺好关联字段 | 为后续"单场利润"核算准备好了干净的台账底数与数据勾稽关系 |
| **IT / 系统管理员** | 权限配置工作量巨大，出错率高，安全审计无依据 | 权限矩阵可配置、SSO 集中管理、操作留痕 | 从"手工配权"转为"规则运维"，工作量和风险同步下降 |
| **高管 / 老板** | 看不到公司到底有多少账号资产、在谁手上、风险在哪 | 资产总览 + 账号持有人看板 + 直播台账 | 第一次能"看清家底"：多少资产、谁在用、风险敞口多大 |

### 3.3 可感知的效果

**对一线员工：**
| 上线前 | 上线后 |
|---|---|
| 入职后申请权限平均要等 **1–3 天**，多个系统分别找不同人 | 钉钉登录即用，权限随岗位模板 **自动到位** |
| 领账号靠微信/口头，不记得自己领了啥 | 个人工作台一屏看到**自己的账号清单和状态** |
| 开播不登记，出问题只能"回忆" | 开播前 **1 次登记**（约 1 分钟），历史随时可查 |

**对管理者：**
| 上线前 | 上线后 |
|---|---|
| 团队权限靠 Excel 记忆，人员变动常漏配 | 权限与组织架构 **自动同步（延迟 < 5 分钟）** |
| 账号发出去就"失联"，离职收不回 | 账号流转/收回全程线上，**离职自动触发归还** |
| 封号后排查靠问人，耗时数小时甚至数天 | 通过资产/直播台账 **分钟级定位责任人 + 设备** |

**对公司经营：**
| 上线前 | 上线后 |
|---|---|
| 数百个账号散落在个人 Excel，公司不知道真实家底 | 资产 **集中上账**，老板一屏看全 |
| 权限安全依赖"人靠谱"，存在合规隐患 | 权限可审计、可追溯，**安全风险显性化** |
| 直播没有数据沉淀，后续无从分析 | 每场直播**留痕率 100%**，为利润分析打好底 |
| 人、资产、场次之间"对不上账"，未来难穿透 | **数据模型定版**，为第三期利润反查、人效盘点铺好路 |

### 3.4 量化验收指标（本期目标）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 权限同步延迟 | **< 5 分钟** | 钉钉人员/岗位变动到系统生效 |
| SSO 登录成功率 | **> 99.5%** | 登录稳定性 |
| 资产关联完整率 | **> 98%** | 资产与实名人/账号的关联完整度。**该指标受存量 Excel 数据质量制约**，须以"可补全部分全部补全 + 无法补全部分列清单说明"为验收口径（见 3.5） |
| 账号领用线上化率 | **= 100%** | 所有领用/归还原走线上 |
| 直播台账留痕率 | **= 100%** | 每场直播都有登记记录 |

### 3.5 交付物与验收标准（含技术验收判据）

| 交付物 | 业务验收标准 | 技术验收判据 |
|---|---|---|
| 权限管理模块（01） | SSO 可用、组织同步自动生效、岗位模板可按岗位一键授权 | SSO 登录成功率 > 99.5%；钉钉事件同步延迟 < 5 分钟；事件订阅失败可补偿 |
| 资产/账号台账（07/08） | 历史 Excel 资产完成迁移入库，关联关系（实名人↔资产↔账号）完整 | 关联完整率 > 98%；正向/反向穿透查询 P95 < 3 秒 |

> **两项必须前置到本期的工作（业务语言）**
> - **指标口径字典 v0（A2）**：如果第二期采集进来的数据没有统一的"口径"（比如"营收"到底算含退款还是不含、按天还是按场次），到第三期做报表时就得把口径重新定义一遍、并且**把历史数据全部重算**。所以第二期在接入采集的同时，先把"口径"定下来。
> - **IP 组两级组织模型（A3）**：第三期的"按 IP 组看利润、按 IP 组下钻报表"都依赖"哪个账号、哪个人属于哪个 IP 组"这个归属关系。如果等到第三期才建，第三期的数据中心和自助报表就无法按 IP 组聚合。因此本期先把这个组织结构搭好。

**关于「05 绩效 ↔ 04 竞品」跨期依赖的处理（A5）**
> PRD 中 05 绩效的指标项包含"竞品分析提交率"，而 04 竞品管理排在第三期（V3）。若照搬，第二期绩效将**取不到竞品数据**。**本方案采用**：第二期绩效**先剔除"竞品分析提交率"这一指标项**，第三期（V3）04 竞品管理上线后再**启用**该指标项。*（备选方案：将 04 竞品管理前移到第二期，但会加重本期范围与集成负担，暂不采用。）*

**关于「13 预警中心」的上线策略（A6）**
> 13 预警中心的价值完全取决于上游是否已产生数据，因此**必须置于第二期收口（V2.3）**。为尽早发挥价值，本期**先上线"预警框架 + 已有规则子集"**（资产到期、账号未归还——这些规则在第一期已有数据支撑），其余规则（证件到期、上报缺失、直播风险、工作流超时、成本未录入、培训逾期、绩效待确认）随上游模块陆续开启。

| 数据中心（12） | 账号穿透 + 利润反查双向可用，全链路看板数据准确 | 穿透查询 P95 < 3 秒；10 万行导出 < 30 秒；数据与源表对账一致 |
| 数据分析（17） | 业务人员可**零代码自助搭建**至少 3 张报表并订阅分享 | 报表查询 P95 < 30 秒；按 IP 组下钻可用 |
| 作品监测（18） | 爆款识别、低效预警规则生效 | 爆款发现延迟 < 1 小时；阈值规则可配置 |
| 组织人效（19） | IP 组模型建立，人效指标完成盘点 | 人效盘点覆盖率 = 100% |
| 竞品资产库（04） | 竞品分析提交—审核—入库闭环跑通 | 竞品分析提交率 > 95%；05 绩效竞品指标项同步启用 |

## 六、跨期价值叠加分析

> IMS 的复利效应在于：**后期的分析能力，全部建立在前期的数据沉淀之上**。单看每期是功能，连起来是一条价值链。

### 6.1 核心价值链条：从"实名人"到"利润"

```
实名人 ── 岗位/权限(01) ── 账号领用(08) ── 资产台账(07) ── 直播台账(10)
   │                                                    │
   └──────────────────────────────────────────► 成本/利润/分成(11)
                                                        │
                              数据中心穿透查询(12) ◄─────┘
                                        │
                              组织人效盘点(19) ◄── 绩效(05)
```

### 6.2 各期数据如何"叠加升值"

| 前期沉淀 | 后期消费 | 复合价值 |
|---|---|---|
| 第一期（V1）：资产/账号台账 + 直播留痕 | 第二期（V2）：单场成本录入、利润计算（11） | 没有"哪场直播用了哪个账号"，成本就无法归集到人 → 利润无从算起 |
| 第一期（V1）：数据模型 + 主体维度预留 | 第三期（V3）：数据中心（12） | 模型不预留，第三期利润反查、实名人穿透无法实现（回填成本极高） |
| 第一期（V1）权限（01）+ 第二期（V2）绩效（05） | 第二期（V2）预警（13） | 绩效自动取数依赖权限/数据打通；低绩效自动预警依赖绩效结果 |
| 第二期（V2）财务核算（11）+ 直播台账（10） | 第三期（V3）数据中心（12） | "从利润反查到责任人"必须同时有利润数据和责任链 |
| 第二期（V2）指标口径字典 v0 | 第三期（V3）数据分析（17） | 口径不前置，第三期需重建口径并**重算历史指标** |
| 第二期（V2）数据采集（16） | 第三期（V3）数据分析（17）/作品监测（18） | 采集是进水管，分析是出水口；没有自动采集，自助分析就是无米之炊 |
| 第二期（V2）IP 组组织模型 + 工作流（14）+ 内容生产（15） | 第三期（V3）作品监测（18）/人效（19） | 内容产出—效果—人效形成完整闭环，人效才有真实产出数据可算 |

### 6.3 一句话总结叠加逻辑

> **第一期（V1）让数据"存在"，第二期（V2）让数据"流动"，第三期（V3）让数据"说话"。** 三者叠加，公司才第一次拥有从**单个实名人**一路穿透到**公司利润与人效**的完整视图。

## 七、非功能需求

> 本章说明系统"跑得快不快、稳不稳、安不安全"这类**不看功能、但天天影响体验与风险**的要求。它不新增业务功能，而是所有业务功能成立的前提。

| 维度 | 要求 | 业务语言解释 |
|---|---|---|
| **性能** | 全链路穿透查询 P95 < 3 秒；10 万行级报表 < 30 秒（预计算下秒级展示，超量走异步导出） | 老板点一个账号就能秒看到全貌，不用等转圈 |
| **可用性** | 钉钉依赖可降级（SSO/同步异常时提供降级登录与对账补偿）；定时任务集群化、无单点故障 | 钉钉偶发故障时，系统不至于全公司停工 |
| **安全** | SSO + 权限分级；证件档案带水印、禁下载、访问留痕审计 | 证件等敏感信息不泄露、被谁看过可查 |
| **容量与存储** | 图片压缩、OSS 生命周期管理、签名访问 | 存储成本可控，不因图片堆积导致费用失控 |
| **备份与容灾** | 主数据与关键事实数据定期备份；关键数据本地留存 | 出故障能恢复，核心台账不丢 |
| **多主体隔离** | 一期即定"主体（公司）维度字段"架构，即使当前单主体也预留 | 未来若成立新公司主体，无需推倒重构（见附录 A 的 A7） |

2. **部门负责人做"种子用户"**：每期上线前先培训部门负责人，再由其带动一线。
3. **分模块小步快跑**：第二期按 V2.1 → V2.2 → V2.3 分批上线，每批上线即推广。
4. **培训与激励挂钩**：将系统使用完成率（日报、培训、上报）纳入部门/个人考核，避免"上线即闲置"。
5. **设"系统管理员"专人**：负责日常运维、规则配置、问题响应，确保系统长期可用。

### 8.4 数据迁移与推广节奏

- **一期必迁（不可后补）**：在职人员、账号/资产台账、**资产↔实名人↔账号关联关系**——这是全链路主键，一期不迁完，10/11/12 全部悬空。
- **可后补**：历史直播场次（迁移后标注"系统前数据"）。
- **可不迁/补录**：历史成本、利润、分成（建议不迁，靠补录或标注"数据不完整"，不参与趋势分析）。
- **推广**：每期上线设 **1–2 周灰度期**，先小范围试用再全员放开；灰度期内保留人工兜底通道。

> **结语**：IMS 不是一次性交付的项目，而是一条**分三期逐步建成的数据价值链**。第一期（V1）止血（权限/资产/直播），第二期（V2）成型（管理闭环），第三期（V3）增值（数据决策）。建议管理层的关注点不是"功能上线了几个"，而是**每一期上线后，业务是否真的从"靠人"走向了"靠系统"**——这才是这套系统真正的价值所在。
