## 0. 结论先行

**推荐方案 C：重写框架层，保留数据模型、需求资产和部分模块代码；各模块按功能点逐条对照后，再决定补齐还是重写。** 不建议继续原样修改补齐（方案 A），也不建议整体推倒重来（方案 B）。

- 问题集中在**框架层**：权限分三层，每个接口都要在多处手工登记；测试种子数据写进了业务接口；改库结构靠启动时执行 ALTER；文件、通知、时间、枚举等通用能力没有统一实现，前端也没有组件库。这几类问题会让每个 bug 修复都可能牵连出新问题（B048 修了 5 次，依次卡在 4 个不同层）。继续补齐等于保留这些问题。
- **业务层有不少可以复用**：187 张表的数据模型、712 个接口里的业务计算、约半数模块的主流程（这些模块的测试通过率已到 64%～86%），以及 PRD、产品规格、882 条已审用例、UI 原型这些需求资产。整体重写会把这些已经花了钱的部分全部丢掉。
- 方案 C 的第一步就是你定的新流程第一步（先拆框架任务），所以几乎没有额外的切换成本。

## 2. 框架层质量【事实 + 具体例子】

### 2.1 鉴权和权限：分三层，每个接口都要手工登记多处（最核心的问题）

一个请求要依次过 3 道检查，每道都靠 **URL 前缀字符串匹配**：

| 层 | 文件 | 机制 | 规模 |
|---|---|---|---|
| ① 功能权限 | `app/perm.py`（160 行）+ `app/menu_catalog.py`（500 行） | `API_RULES` 用 URL 前缀映射到权限码，取最长前缀；没匹配上就 403「无操作权限」 | `API_RULES` 69 条；`FUNCTION_SKIP` 白名单 5 条；另有 `USER_FORM_READS`、`EXTRA_ROUTES` 两个特例表 |
| ② 数据范围 | `app/scope.py`（769 行） | `PREFIXES` 把（方法，URL 前缀）映射到表，再到 `SPECS[表]` 取规格；没匹配上就 403「无数据权限」 | `PREFIXES` **334 条**；`SPECS` 103 张表（全库 187 张）；`WHITELIST_PREFIXES` 6 条；对 `/report/submit` 等路径写了专门的 if 分支 |
| ③ 业务内的角色判断 | 各业务模块 | 直接比较 `role_key`、角色名的子串 | 22 个文件里有 **157 处**硬编码角色（不算 seed 和 role_matrix） |

问题和例子：
- **新增一个接口要改 3～5 处**：router、`menu_catalog.API_RULES`、`scope.PREFIXES/SPECS`、`role_matrix`，还有前端的 `nav/catalog.json` 和 `router`。漏掉任何一处都会 fail-closed，表现成「网络错误」「无数据权限」「无操作权限」。BUG-01/02（P0，所有账号都能看到全部菜单）、B048、C054、C056 都属于这一类。
- **同一个修复要在两个白名单里各加一遍**：`/admin-api/ims/train/study` 同时出现在 `perm.FUNCTION_SKIP`（第 21 行）和 `scope.WHITELIST_PREFIXES`（第 20 行）。
- **行级数据范围只有少数模块在用**：消费 `request.state.scope` 的只有 12 个文件（fin、live、meet、bi_*、dc_* 等）。`train.py`、`acct_flow.py`、`flow.py`、`perf.py`、`report.py` 的 `state.scope` 引用都是 0，各自写了一套判断（例如 `train.scoped_user_id`、`live.restrict_sessions`）。
- **按角色名判断业务**：`flow.py:626` 写的是 `key in {"r4","dept_leader",...} or "部门负责人" in name or "运营总监" in name`；`fin.py:92` 写的是 `tags & {"r1","r3","r4","sys:admin"}`；`live.py:500` 写的是 `role_key ... endswith(":r4")`。角色一改名或新建自定义角色，业务就会出错，这和 PRD 里「角色可配置」的要求冲突。
- **代码变动集中在这几个文件**（integ-b4 上的提交数）：`scope.py` 119 次、`main.py` 112 次、`models.py` 140 次、`role_matrix.py` 16 次。4 个切片并行时，大家都在改这几个文件，合入时互相覆盖，这和小白提醒「#186 分支里的 perm.py 是旧版，不要整体覆盖」是同一件事。

### 2.2 数据模型和迁移

- **模型集中在一处，这一点可以保留**：IMS 的 148 张表在 `models.py`（2,760 行），OPS 的 34 张在 `ops_models.py`。统一使用 `tenant_id`（200 处）、`deleted` 软删（116 处），并有 369 处索引声明。
- **没有外键**：`ForeignKey` 0 处，引用完整性全靠代码保证。
- **迁移方式混乱**：
  - 主路径是 `Base.metadata.create_all(engine)`（`main.py:1180`），它不会给已有表加列。
  - 于是 `main.py` 里有 **34 个 `ensure_*_columns()` 函数**，在启动时执行 `ALTER TABLE` 补列（例如 `ensure_perf_record_score_lines`）。
  - 另有 `db/compat/` 下 34 个手写 SQL 补丁，`db/migration/` 只有 2 组正式迁移（0001 auth、0002 sys）。`sqlc.yaml` 是一份 Go 工具链的残留配置，没有被使用。
  - 结果是**库结构由「启动顺序 + 补丁」决定**，换一个库或回滚都没法保证一致。
- **种子数据**：15 个 `*_seed.py`，共 2,572 行。

### 2.3 测试数据混进了生产代码（直接导致「E2E 用 admin 跑通」的假象）

- **业务查询接口会顺手写入 E2E 数据**：
  - `corp.py:913` 证件分页 `certificate_page()` 里调用了 `ensure_cert_e2e_seed(db, actor)`；
  - `workbench.py:93` 工作台 `dashboard()` 里调用了 `ensure_workbench_e2e_seed`；
  - `bi_report.py:1072` 报表列表里调用了 `ensure_bi_br212_seed(db)`；
  - `workbench.flow_pending_count()` 里调用了 `seed_flow` 和 `sync_seed_tasks`。
  - 前两个只在 `username == "admin"` 时触发。也就是说，**admin 打开页面就会自动有数据，别的角色打开就是空的**，所以 E2E 用 admin 跑全绿，测试用角色账号一点就挂。B084「作者下拉只有 E2EClosureAuthor」就是这么来的。
- `main.py` 启动时执行 `_ensure_tc_fill_author`、`_ensure_e2e_ops_author`、`_retire_bi_tc_r9` 等，写入「TC-作者甲」「TC-ACCT-JIA」这类测试数据（`main.py` 里有 71 处 TC/E2E 字样）。`_lifespan` 每次启动都会执行 `commit_e2e_legacy_roles()`。
- `role_matrix.py` 里写死了 tc_r2～tc_r11 测试账号和手机号。

### 2.4 通用能力：各模块各写一套

| 能力 | 现状 |
|---|---|
| 文件存储 | `content_file.storage` 有一个统一实现，但只有 air、api、content_task、train 4 个文件在用。`cert_original.py` 自己写了一套 `file_root()/stored_path()`，`asset_export.py` 又写了一套 `data/ims-files` 路径，`asset_purchase.py` 直接 `file.file.read()` |

### 2.5 前端框架

- `package.json` 声明了 element-plus 依赖，但 views 里 **`<el-` 组件使用次数为 0**。页面全是手写 HTML：`<input>` 666 处、`<select>` 439 处、`<table>` 227 处，样式来自 `styles/prototype.css`（等于把原型 HTML 直接搬了过来）。
- 公共表单组件 `components/form/*` 只有 9 个页面在用。**没有人员、账号、部门、字典这类选择器组件**，所以有 16 处表单要用户手填「用户 ID」「账号 ID」「方案 ID」（如 `perf/execution.vue:189-190`、`collect/log.vue:27`）。测试登记的 BUG-029、C005、C009、C054 都是这个问题。
- 前端没有按模块拆分的 API 层（`src/api` 只有 `http.ts`、`read.ts`），views 里直接写了 801 处 `/admin-api` 地址。前后端契约没有类型定义来约束。

### 2.6 工程卫生

- `ims-backend/` 根目录下有 65 个 `pytest_*.txt`、`token.txt`、`login_out.json` 之类的临时输出文件被提交进了仓库。
- E2E 的 265 个 spec 里有 246 个直接 `page.goto(URL)`（共 641 次），只有约 12 个是从菜单点进去的，只有 39 个用到了角色账号。这和你说的「E2E 只验证接口/页面通了」一致。

共性问题：
1. **每个模块一个两三千行的大文件**，路由、Pydantic 模型、业务逻辑、查询、VO 组装全写在一起，没有 service/repository 分层。
2. **数据范围有 3 种写法**：用 `state.scope` 的、自己写 restrict 函数的、什么都没做的。所以同一类「角色看到的数据不对」问题会在不同模块反复出现。
3. **前后端契约不对齐的典型表现**：后端返回 ID 和英文枚举，前端没有统一转换（部门显示「部门#7301」、状态显示 `IN_PROGRESS`）；表单要手填 ID；后端字段齐了，前端页面却缺字段（BUG-014 新建大组只有组名和等级）。
4. **业务逻辑本身大多能用**：例如财务三级利润、分成、结账，培训指派和完成率，考试和绩效计算，这些后端规则测试多数能走通，失败主要集中在入口、权限和展示层。这部分是值得保留的资产。

## 6. 三个方案

### 方案 A：修改补齐（沿用现有框架，继续修 bug 加补功能）

- **可保留**：几乎全部。
- **仍要做的**：
  1. 约 128 条未关闭的 bug；
  2. 还没执行的 TC-02、TC-23 和各模块未执行、阻塞的约 200 条用例；按目前每执行一条约 0.4 个 bug 的比例（288 个 bug / 约 690 行），预计还会冒出 **80～120 条**【估算】；
  3. 按新流程本来就要做的功能点清单，对出来的「功能缺失」还没被量化（现在只覆盖到用例写到的部分）。
- **风险**：
  1. §2 的结构问题全部保留。每加一个接口都要改 3～5 个登记表，`scope.py`、`main.py`、`models.py` 继续是冲突热点，B048 式的多层返工会持续出现。
  2. 测试种子还在业务接口里，admin 和角色账号看到的数据不一样，以后 UAT 结论不可信。
  3. 没有迁移工具，上线时库结构没法可靠复现。
  4. 前端没有组件库和选择器，「手填 ID」「英文枚举」这类 bug 只能一页一页地修。

### 方案 B：整体重新开发

- **可复用**：PRD、产品规格（32 份页面规格 + 32 份 API 契约）、882 条已审用例、UI 原型、187 张表的数据模型（作为设计参考）、业务计算规则（作为参考实现）、技术栈（FastAPI、Vue3、MySQL）。
- **风险**：
  1. 工作量最大：要重做 712 个接口、约 121 个页面。
  2. 约半数模块已经有 64%～86% 的用例能通过，这部分会白白丢掉。
  3. 重写本身也会产生一批新 bug，同样要走测试和回归。
  4. 外部对接（钉钉、Football、采集桩、AI 网关）要重新联调。

### 方案 C（推荐）：框架层重写，模块按功能点对照后分档处理

1. **框架层重写**（对应新流程的第一步）：
   - **权限**：改成声明式。接口在路由上直接声明权限码和数据范围（装饰器或依赖），数据范围在查询层统一注入。取消 URL 前缀表（`API_RULES`、`PREFIXES`、两个白名单），也取消业务里按角色名判断的写法，改成配置化的「审批人或角色能力」。
   - **数据**：引入 Alembic，以当前 187 张表为基线生成第一个迁移，删掉 34 个 `ensure_*` 和 `db/compat`。补上必要的外键和约束。
   - **种子**：清理所有业务接口和启动流程里的种子写入，只保留一份「最小初始化」种子（菜单、字典、admin）。E2E 和测试数据由测试自己通过界面造出来。
   - **通用服务**：文件存储、待办/消息/通知、操作日志、时间格式、字典和枚举、编号生成，各做一份统一实现。
   - **前端**：落地组件库，抽出 UserSelect、AccountSelect、DeptSelect、DictSelect、状态标签、时间格式、表格和分页等公共组件，按模块拆出 API 层。
   - **工程**：把后端按模块分包（router、schema、service、repo），清理仓库里的临时文件。
2. **模块分档**：每个模块先由产品经理拆出功能点清单，开发拿清单对现有代码逐条标「已实现 / 部分 / 缺失」，再按以下规则处理：
   - **补齐档**（当前通过率 ≥60%：内容生产、竞品、作品监测、会议日报、数据采集、培训）：保留业务代码，接入新框架，补齐缺失的功能点。
   - **重写档**（通过率 ≤33% 且功能缺失多：系统管理/权限、公司资产、IP 组、直播、财务、工作流、绩效/考试、数据报表、指标、数据分析、预警、工作台）：参考现有表结构和后端计算逻辑，重写前端页面和接口层，业务计算能复用的直接搬过来。
   - **中间档**（内部分析、AI 资源中心、数据上报）：对照功能点后再定。
3. **风险**：框架改造期间，所有模块都要重新接入一次，等于整体回归一遍。不过新流程本来就要求按模块提测，这一轮回归可以和提测合并。

## 8. 推荐和理由

**推荐方案 C**，理由：

1. **问题根源在框架层**：权限三层前缀登记、种子混进业务接口、启动时 ALTER、没有通用组件。这些问题在 bug 里分别占权限 17%、展示 23%、数据 13%，修补只能一条一条地压，压不完。重写框架层可以一次性消除这几类问题，和你定的「先做框架任务、用单测验证」完全一致。
2. **功能缺失（38%）不管选哪个方案都得补**，而且都要先有功能点清单。方案 C 让每个模块先对照清单再决定补还是重写，代码量最少，判断也有依据。
3. **保留已经花了钱的部分**：数据模型、需求资产、约半数模块的业务代码。用量和日历时间都比整体重写省约三分之一。
4. **方案 A 看起来便宜，但没有封顶**：修 bug 平均每条约 90 次调用，B048 这类多层返工会持续出现；而且 A 结束后代码仍然不可维护，UAT 结论也不可靠。

**建议的下一步**（不需要额外切换成本）：
1. 产品经理先拆**框架任务清单**：权限和数据范围声明式改造、Alembic 基线、种子清理、文件/通知/待办/时间/字典服务、前端组件库和选择器、后端分包。交给你审核。
2. 同时，产品经理按「模块 → 页面 → 功能点」拆清单。拆好一个模块，就让开发拿现有代码做一遍「已实现 / 部分 / 缺失」对照，按对照结果把这个模块归入补齐档或重写档，再交你审核。
3. 框架完成并通过单测之后，按业务依赖顺序逐个模块开发、提测、回归，最后做 UAT。
